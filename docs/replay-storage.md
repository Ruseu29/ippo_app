# リプレイの保存設計

## 決めた構成

Supabase は既存の `play_results` だけを使う。1操作1行のまま、本文は保存しない。
タイトル・本文・読みは、`src/data/stories/<作品ID>/prompts.json` に作品別で保存し、`src/data/prompts.ts` から読み込む。作品の追加時はこの一覧にも登録する。フォルダを移動しても、既存の文章ID・本文・文の区切りは維持する。

| 項目 | 例・意味 |
| --- | --- |
| `session_id` | 1プレイをまとめる UUID |
| `prompt_id`（追加） | `buying-mittens-opening` → 手袋を買いに（1） |
| `sentence_number`（既存） | 1から始まる、その文章内の文番号 |
| `event_index`（既存） | 0から始まる操作順。同時刻でも順序を確定 |
| `is_injected`（追加） | 自動修正で追加したBackspace・文字はtrue。通常操作はfalse |

`NextSentence` は移動前の文番号、`Finish` は終了した文番号で記録する。
実際に受け付けた進行だけを記録し、両方の `delta_ms` は null。
無効な Enter/Space も実キーの生ログとして残す。打鍵間隔の計測方法は維持する。
新規ログの`version`はアプリの`src/logic/logger.ts`（LOG_VERSION）で`1.2`を付け、
テスト作品（prompt_id = test-1）だけは識別用に`-11.0`（TEST_LOG_VERSION）を付ける。
端末保存・Supabase送信でも生成時の値を維持する。旧1.1ログの再送も1.1のまま。
Supabaseの既定値も1.2に揃えるが、版番号の省略されたINSERTにだけ使われる。
再生・送信は1.1・1.2・-11.0に対応し、1.2と-11.0ではis_injectedの真偽値を必須とする。

検証条件を揃えるため、今回のテスト版 `-11.0`（`test-1`）の本文・読み・文順は次の2文で固定する。

1. 一石二鳥ってどういう意味でしょうか？（いっせきにちょうってどういういみでしょうか？）
2. 山では大変な騒ぎになったそうです。（やまではたいへんなさわぎになったそうです。）

自動修正も1キー1行で元のログの後ろへ追記し、event_indexを連番にする。
注入操作のdelta_msはnullとし、実打鍵の間隔・回数・Backspace回数には含めない。
旧端末ログのis_injected未指定はfalseとして扱う。再生時は辞書を再実行せず、
保存された注入キーをそのまま反映する。注入した文字と、それを含む仮名は青色で表示する。

## 公開ページでの臨時辞書

開始画面の「修正辞書を一時編集」を開き、JSONを編集して「このタブに適用」を押す。
形式と修正手順を検証し、正常な場合だけ辞書全体を差し替え、自動修正をONにする。
タイトルに戻る・「もう1回する」では適用を保つ。再読み込み・別タブでは標準辞書に戻る。
「標準に戻す」でも元に戻せる。GitHubのファイルや他の利用者の辞書は書き換えない。

「JSONを保存」は編集中の辞書を `corrections.json` としてダウンロードする。
保存だけではプレイに適用しない。残したい変更は再読み込み前に保存し、後で内容を確認して
`src/data/corrections.json` に取り込む。保存済みJSONを再び試す場合は編集欄に内容を貼り付ける。
プレイのログ・保存先・バージョンは従来と同じで、リプレイには実際の注入操作が残る。

## 保存場所と流れ

1. 入力中は React のメモリに保持。
2. 完了時、Finishを追加したデータを IndexedDB `ippo-replays` / `plays` に未送信として保存。
3. 全操作を `play_results` へ一括送信。成功後は端末の状態を送信済みにする。
4. 通信失敗時は未送信のまま残す。画面を再読み込みしても再送できる。

同じ `(session_id, event_index)` の再送は無視し、既存行を上書きしない。
これには一意索引が必要。独自SQL関数・RPC・追加テーブルは使わない。
完了前の入力は再読み込みすると失われる。端末保存は同じブラウザ・同じオリジン内だけ
（localhostのポートが変わると別の保存先）。容量不足時は警告し、メモリとオンライン送信を使う。

## 読み取りと画面の記憶

起動時に、現在の問題一覧にある `prompt_id` の最新10件の Finish を検索する。
その `session_id` に属する全ログを、APIの返却上限を超えてもページを分けて取得する。
途中のログが欠けていれば再生用データとして扱わず、エラーを示す。
取得結果は React の状態に保持し、履歴画面を開くたびには通信しない。
新規送信成功分はメモリへ追加。手動更新も可能。表示だけ10件に絞り、保存データは削除しない。

オンライン全体と、この端末の履歴を切り替えられる。端末は最新10件に加え、
古い未送信分も再送用に読み込む。起動時のオンライン取得失敗は端末履歴を妨げない。

再生は最初のログを0msとし、`perf` の差で進める（最初の打鍵までの待ち時間は保存しない）。
問題文を修正すると過去の再生も現在の本文・読みになる。削除されたIDや文数の不一致、
未対応のログ版ではログ閲覧のみ。文章IDのない旧DB行は推測して補わず、オンライン一覧に含めない。

端末内形式は schema_version 2（ログの version 1.2 とは別）。旧案の schema_version 1 は
明示的な文章IDと操作順がある場合だけ移行し、本文スナップショットを外す。
判別できない旧データは削除せず残し、自動再送から除外した旨を表示する。

## Supabase側の準備

- 確認用：`supabase/inspect-replay.sql`。現在の列、権限、ポリシー、重複を調べる。
- 必須：`supabase/migrations/202609230001_replays.sql`。prompt_id列、一意索引、Finish検索用索引を追加する。
  既存のevent_index・sentence_number・version既定値1.1は変更しない。重複があれば削除せず失敗する。
- 自動修正を保存する前に：`supabase/migrations/202609280001_injected_input.sql`。
  is_injected列を追加する。未適用のDBでは送信が失敗し、端末の未送信ログを保持して再送を待つ。
- 続けて：`supabase/migrations/202609280002_log_version_1_2.sql`。
  versionの既定値を1.2にする。既存行の版番号は書き換えない。
- 読み取り：`supabase/enable-dev-replay-read.sql`。anonにSELECTを許可し、
  `permission = 'web_test' AND prompt_id IS NOT NULL` の行だけ読むポリシーを設定する。
  GUIで同名の「Allow web test replay reads」を作成済みなら二重に作る必要はない。

RLSは有効のまま。既存INSERTポリシーと書き込み権限は維持する。
開発用の全体履歴なので、読み取り条件に合う行は公開キーを使う第三者も取得できる。
**10件は画面の表示制限であり、アクセス制限ではない。** ユーザー別履歴にする際は認証とRLSを設計し直す。
正常な空配列だけでは「該当なし」と「RLSで非表示」をアプリから区別できない。

## ローカル検証

`pnpm test`：操作順、長いプレイの全件取得、版番号の維持、一括保存、再送、RLS、旧端末データの移行。
DBテストはPGlite内だけで実行し、実Supabaseへ接続しない。`pnpm build`：型とビルド。

UI検証：`pnpm exec tsx tests/browser-server.ts` → `http://localhost:5186`。
短い検証問題と模擬DBの12プレイを使用する。初期状態は送信失敗。
端末保存と再読み込みを確認後、別のPowerShellから
`Invoke-RestMethod http://127.0.0.1:5187/allow-writes -Method Post` で送信を許可する。
`http://127.0.0.1:5187/stats` のreadsで画面の往復が追加取得を起こさないことを確認できる。
ソースの問題文・実Supabaseは変更しない。
